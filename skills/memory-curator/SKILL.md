# Memory Curator

定期审计 project-memory/，防止知识腐化，保持 Memory 质量。

---

## Memory 契约

### 始终加载（每次执行前必读）
- `project-memory/MEMORY.md` — Memory 索引，审计的入口
- 所有 `project-memory/*.md` 文件（审计对象）
- `rules/**/*.md` — 各 Workbench 工程规范（编码/接口/库），审计对象

### 执行后写入（草稿，必须人工确认后才执行）
- 任何 `project-memory/` 文件的修改（删除、更新、归档）
- 操作清单写入 `docs/memory-audits/{date}-audit-report.md`

---

## 输入

无强制输入。触发即开始全量审计。

可选：指定审计范围（`glossary` / `adrs` / `constraints` / `rules` / `all`，默认 `all`）

---

## 输出

```
docs/memory-audits/
└── {date}-audit-report.md    # 审计报告（含草稿操作清单）
```

**所有修改都写入报告作为草稿，不直接修改任何 Memory 文件。**

---

## Guardrails

| 规则 | 触发条件 | 执行动作 |
|------|---------|---------|
| **禁止自动修改** | 审计完成时直接修改 Memory 文件 | BLOCK：所有变更必须写入报告草稿，等待人类确认 |
| **禁止自动运行** | 任何非人类显式触发的执行 | BLOCK：只能由人类手动触发 |
| **删除需要证据** | 提议删除某个术语/规则但无充分理由 | BLOCK：删除操作必须说明"为何认为已过时" |

---

## 执行流程

### Step 1：扫描术语表（project_glossary.md）

- **候选废弃**：术语在近期需求文档和代码中从未出现
- **候选更新**：术语定义与最新代码/文档存在出入
- **候选新增**：需求文档中频繁出现但术语表中没有的词

### Step 2：扫描架构约束（architectural_constraints.md）

- **候选废弃**：约束对应的功能已下线或技术方案已替换
- **候选弱化**：约束从"BLOCK"降级为"WARN"的候选
- **候选新增**：近期频繁违反但未成文的约束

### Step 3：扫描 ADR（adr_index.md + adrs/）

- **候选归档**：ACCEPTED 状态但对应决策已被推翻
- **候选确认**：PROPOSED 状态超过 30 天未变更
- **待补充**：近期有重要架构选型但无对应 ADR

### Step 4：扫描工程规范（rules/{Workbench}/ 编码/接口/库规范）

逐 Workbench 扫描 `rules/{Workbench}/coding.md`、`api.md`、`database.md`（存在者）：
- **候选废弃**：规范条目与实际代码习惯不符
- **候选更新**：规范引用了已升级的框架版本或 API

### Step 5：生成审计报告

写入 `docs/memory-audits/{date}-audit-report.md`：

```markdown
# Memory 审计报告 — {YYYY-MM-DD}

**审计范围**：{all / glossary / adrs / constraints / rules}
**审计人**：（由执行者填写）
```

## 关键原则

1. **草稿不执行**：所有变更建议都是草稿，人工确认后才执行
2. **证据为王**：废弃提议必须有具体理由，不凭"感觉过时"删除
3. **每两周一次**：不频繁审计（增加噪音），也不间隔太长（知识腐化加速）
