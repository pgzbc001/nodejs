# PRD Writer

将需求描述转化为结构化 PRD 文档，遵循标准模板，聚焦业务逻辑。

---

## 输入

| 输入 | 必填 | 说明 |
|------|------|------|
| **需求描述** | **是** | 用户直接粘贴的文字描述，或已有文档的路径 |
| **输出路径** | 否 | PRD 文件保存路径；未提供时默认输出到 `{{REQUIREMENTS_DIR}}/{功能名}/prd.md` |

---

## 输出

```
{output_path}/prd.md    # 按模板生成的 PRD 文档
```

**模板结构**（严格遵循 `doc-templates/07_prd_template.md`）：

```markdown
# 需求描述
{总结性描述，让人直观了解需求范围}

## 核心场景及产品逻辑定义

### 用户故事#1：{Description}

【前提条件】

【验收标准】

### 用户故事#N：{Description}

【前提条件】

【验收标准】
```

---

## Guardrails

| 规则 | 触发条件 | 执行动作 |
|------|---------|---------|
| **禁止模板说明性文字** | 输出包含模板中的占位说明（如 `{此处…}`、"要求…"等提示语） | BLOCK：移除所有模板说明，只保留实际需求内容 |
| **禁止技术命名** | 输出中出现代码变量名（camelCase/snake_case）、目录结构、接口路径 | BLOCK：替换为业务语言描述的字段名 |
| **禁止排版细节** | 输出描述颜色、左右位置、字体大小、高亮方式等视觉信息 | BLOCK：删除，改为描述"展示 X 信息"/"支持 X 操作" |
| **禁止技术规范章节** | 输出包含视觉规范、交互规范、页面路由、接口需求、非功能性需求等章节 | BLOCK：整章删除，不保留 |
| **数据字段必须明确** | 涉及数据展示或录入，但未列出具体字段名 | WARN：在对应用户故事下补充字段清单，使用业务语言命名 |
| **用户故事必须完整** | 任意用户故事缺少【前提条件】或【验收标准】 | BLOCK：补全后再输出 |

## 执行流程

### Step 1：理解需求输入

1. 若用户提供文档路径 → 读取文档内容
2. 若用户直接粘贴文字 → 直接使用
3. **若需求描述不足以生成有意义的用户故事**（信息过少、目标不明）→ 列出具体缺失项，等待用户补充；不猜测、不自行填充

---

### Step 2：拆分用户故事

将需求描述拆解为独立的业务场景，每个场景对应一个用户故事。拆分原则：

- **按功能点而非页面**：同一页面上的不同功能拆为独立故事
- **按角色区分**：不同用户角色使用同一功能时，分别建立故事
- **按流程节点**：一个完整流程的关键节点（触发、处理、结果）可拆为独立故事，也可合并，以"能否独立验收"为判断标准

---

### Step 3：生成 PRD 文档

按以下规范逐节生成：

#### 需求描述（首段）

- 1-3 句话总结：当前文档描述的是什么功能、面向哪类用户、解决什么问题
- 不需要技术背景描述

#### 用户故事

每条用户故事格式：

```
### 用户故事#N：{一句话描述这个场景}

【前提条件】
- 用户处于什么状态/角色下
- 系统处于什么前置状态（如有）

【验收标准】
- WHEN {触发条件} SHALL {期望结果}
- （多条 AC 逐条列出）
```

**数据字段处理规则**：
- 需要展示数据 → 列出"展示字段"清单，用业务语言命名（如"姓名"、"订单状态"）
- 需要填写/录入数据 → 列出"必填字段"和"选填字段"
- 字段有业务规则（如状态值、枚举） → 在验收标准中明确列举所有可能值及含义

---

### Step 4：自检

生成后自动执行以下检查，不通过则修复后输出：

| 检查项 | 通过标准 |
|--------|---------|
| 无模板说明性文字 | 输出中不含 `{...}` 占位符或原模板提示语 |
| 无技术命名 | 字段名使用业务语言术语 |
| 无视觉/布局描述 | 不含颜色、位置、排版信息 |
| 无技术规范章节 | 不含视觉规范、接口规范、路由说明等章节标题 |
| 用户故事完整 | 每条故事含【前提条件】和【验收标准】 |
| 数据字段明确 | 涉及数据的故事均列出具体字段 |

---

## 输出风格规范

**用产品经理的语气**，不用工程师的语气：

| 避免 | 改为 |
|------|------|
| "调用 /api/users 接口获取数据" | "展示用户列表" |
| "前端渲染 `staffCode` 字段" | "展示员工编号" |
| "右侧 panel 宽度 320px，背景色 #F5F5F5" | "侧边展示详情信息" |
| "点击按钮触发 POST 请求" | "提交后系统保存记录" |
| "非功能性需求：响应时间 < 200ms" | （整段删除，不保留） |

---

## 关键原则

1. **业务逻辑优先**：每条验收标准描述"用户能做什么"或"系统呈现什么"，而非"系统怎么实现"
2. **字段足以指导开发**：涉及数据的地方，开发者读完 PRD 应能明确知道需要哪些字段
3. **不推断缺失信息**：需求不明确时提问，而非猜测后填充
4. **模板结构不变**：只有两个顶层章节（需求描述 + 核心场景及产品逻辑定义），不增加其他章节
