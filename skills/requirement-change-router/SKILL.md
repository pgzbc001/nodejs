# Requirement Change Router

当需求变更或失误时，路由影响范围，标注失效产物，产出重跑清单。

> **适用时机**：本 Skill 用于**同一 ticket 编码完成之后**才发生的需求变更——此时各阶段产物（需求/设计/代码/测试）均已固化，变更会"使下游产物失效"，需要路由出有序重跑清单。
> 编码尚在进行中的需求调整**不走本 Skill**：直接更新对应在产文档即可，无失效路由问题。

---

## Memory 契约

### 始终加载（每次执行前必读）
- `local_profile.yaml` — 获取 role；用于跨 Workbench/C 类变更的爆炸半径门控
- `{{REQUIREMENTS_DIR}}/{ticket-id}/cross-Workbench-review.md` — 若存在则加载，作为跨 Workbench 触点判定依据
- `{{REQUIREMENTS_DIR}}/{ticket-id}/_progress.md` — 读取当前流程进度
- `project-memory/project_glossary.md` — 判断变更是否影响术语体系

### 执行后写入
- `{{REQUIREMENTS_DIR}}/{ticket-id}/_progress.md` — 追加变更记录、标注失效产物状态为 ⚠️、**落盘本次变更的重跑清单**（含执行者/前置条件/完成勾选）

## 输入

| 输入 | 必填 | 说明 |
|------|------|------|
| **票据 ID** | **是** | `{{TICKET_PREFIX}}-xxxx` |
| **变更描述** | **是** | 具体改了什么（功能点或字段级别），不接受"需求改了"这类无信息输入 |
| 更新后的 PRD 路径 | 否 | 如 BA 已更新 PRD 文件，提供路径供分析参考 |

---

## 变更分类标准

| 类型 | 定义 | 失效范围 |
|------|------|---------|
| **A 澄清/笔误** | 只改表述，不增减功能点，不改字段类型/数量/Workbench 范围 | requirements.md 对应段落；下游引用该段的设计文档标注 ⚠️ |
| **B Workbench 内变更** | 功能点有增删，但涉及 Workbench 不变 | 受影响 Workbench：impact_analysis → requirements → design → 代码 → 测试 |
| **C 重大变更** | 新增 Workbench、改核心状态机、推翻架构决策、影响多 Workbench | 需求启动（requirement-kickoff）之后所有已完成产物 |

**分类模糊时**：不自动选最保守的 C，生成具体澄清问题交给人类回答。

## Guardrails

| 规则 | 触发条件 | 执行动作 |
|------|---------|---------|
| **跨 Workbench/重大变更越权** | role 非 dev-lead 且（分类为 C **或** 命中跨 Workbench 触点） | BLOCK：升级 Dev Lead 执行 |
| **跨 Workbench 触点漏判** | 分类为 A/B，但变更触碰 cross-Workbench-review.md 中记录的契约/共享资源 | BLOCK：重新评估为跨 Workbench 变更，升级 Dev Lead |
| **流程未启动** | `_progress.md` 不存在 | BLOCK：需求分析尚未开始，直接更新 PRD 文件即可 |
| **编码阶段未完成** | `_progress.md` 中编码阶段（feature-developer）状态非 ✅ | BLOCK：本 Skill 用于**编码完成后**的需求变更失效路由；在制品阶段的需求调整请直接更新对应在产文档，无需走失效路由。 |
| **变更描述缺失** | 用户未提供具体变更内容 | BLOCK：要求提供功能点/字段级别的具体变更描述 |
| **分类未确认禁止写入** | 变更分类尚未经人类确认 | BLOCK：确认前不修改 `_progress.md` 任何内容 |
| **禁止修改文档** | 尝试修改需求/设计/代码文档 | BLOCK：此 Skill 只写 `_progress.md` |

## 执行流程

### 前置条件检查

-1. 读取 `local_profile.yaml`（记录 role，爆炸半径门控在 Step 1.5 后执行）
0. 读取 `{{REQUIREMENTS_DIR}}/{ticket-id}/_progress.md`：
    - 不存在 → BLOCK
    - **编码阶段（feature-developer）状态非 ✅ → BLOCK**：本 Skill 仅处理编码完成后的变更（见「适用时机」），在制品阶段请直接更新对应在产文档
1. 读取变更描述（用户提供）

---

### Step 1：变更分析与分类建议

分析：
1. 变更涉及哪些用户故事/功能点/字段
2. 已完成产物中哪些覆盖了被变更的内容
3. 变更是否触碰跨 Workbench 触点（跨 Workbench 契约/共享资源/多 Workbench 字段命名）
4. 给出初步分类（A/B/C）+ 理由

以表格呈现判断结果：
- 变更分类建议 + 判断理由
- 跨 Workbench 触点（无/命中）
- 受影响产物列表（路径 + 失效原因）
- 不同分类时的影响范围差异

---

### Step 1.5：爆炸半径门控

| 条件 | 确认人 | 动作 |
|------|-------|------|
| 分类 A/B **且** 无跨 Workbench 触点 | 本 Workbench 工程师 | 工程师自行确认后进入 Step 2 |
| 分类 C **或** 命中跨 Workbench 触点 | Dev Lead | 若 role 非 dev-lead → BLOCK 升级 |

**完成后 BLOCK**：等待门控人确认分类及受影响产物列表。

---

### Step 2：确认后写入变更记录【门控后执行】

**2.1** 在 `_progress.md` 的"需求变更记录"区块追加：
```
| v{n+1} | {YYYY-MM-DD} | Type {A/B/C} | {变更描述摘要} | {影响 Workbench} |
```

**2.2** 在"流程进度"表中，将受影响的已 ✅ 阶段状态改为 `⚠️ 待重审（v{n+1}）`

**2.3** 在"贡献记录"区块追加变更记录

**2.4** 在 `_progress.md` 的"需求变更记录"区块、本次变更行下方，追加本次变更的**重跑清单子表**（内容见 Step 3）

> 重跑清单**必须落盘到 `_progress.md`**，不只在对话中输出。理由：编码后变更的失效链常横跨多 Workbench、多名工程师、多个会话；`_progress.md` 是团队唯一的跨会话/跨人协调信号，`⚠️ 待重审` 标记必须与"谁、按什么顺序、满足什么前置去重跑"的清单绑定，换人接手才不丢上下文。

---

### Step 3：生成并落盘重跑清单

将下表写入 `_progress.md`（Step 2.4 的位置），**并同时在对话中输出**供门控人即时查看：

```
### 重跑清单（v{n+1}，Type {A/B/C}）

| 优先级 | Skill | 执行者 | 前置条件 | 操作说明 | 完成 |
|--------|-------|-------|---------|---------|:---:|
| 0 | requirement-kickoff | BA/Dev Lead | 无 | 仅 Type C 新增 Workbench/改派活时重跑（重新检测 Workbench、第一轮业务澄清、派活） | ☐ |
| 1 | impact-analyzer | {Workbench}工程师 | 无 | 按「文档历史保留约定」更新 | ☐ |
| 2 | cross-workbench-reviewer | Dev Lead | impact-analyzer ✅ | 仅跨 Workbench 需求执行 | ☐ |
| 3 | requirements-analyst（汇总） | BA/Dev Lead | 跨 Workbench Review ✅ | 第二轮技术 Q&A + 汇总；核心产物需快照旧版 | ☐ |
| ... | ... | ... | ... | ... | ☐ |

不受此次变更影响（无需重跑）：
- {阶段名}：{原因}
```

> 「完成」列供各执行者重跑后自行勾选，使 `_progress.md` 同时承载"哪些产物失效"与"失效产物已重跑到什么程度"。重跑清单条目与 Step 2.2 标 `⚠️` 的阶段一一对应——每个 ⚠️ 阶段必须在清单中有对应重跑行，不允许只标失效不给重跑路径。

## 文档历史保留约定

> 供下游 Skill 重跑时遵守的统一写入规范。

### 核心原则：增量更新到当前目标态，不整篇重生成

重跑时**不是**把文档重新生成一遍覆盖掉，而是以现有文档为基线，把本次变更作为 delta 应用进去，使正文成为最新的「当前目标态」。

> **为什么不整篇重生成**：编码后阶段的文档已承载大量经人工门控敲定的决策（A 表设计、边界条件、取舍）。整篇重生成会让 AI 把注意力集中在本次变更上，**静默丢失或改写仍然有效的旧内容**——这种错没人会发现，最危险。增量更新保住已敲定的资产，且让门控人只需 review delta。

**判定文档属哪种类型，决定写入方式：**

| 文档类型 | 定义 | 重跑写入方式 |
|---------|------|------------|
| **累积目标态文档** | 描述系统最终应长成什么样（requirements / design / solution-design / api / schema / 测试用例 / 造数脚本等） | **增量更新**（见下方三条硬约束） |
| **针对当前现实的 delta 文档** | 描述"从当前代码出发要改什么"（仅 `00_impact_analysis.md`） | **覆盖**——重跑是针对已改过的代码重新推导，旧版天然作废；但仍保留履历表头记一句"为何重新分析" |

### 累积目标态文档的三条硬约束

1. **delta 可增 / 可改 / 可删**：变更不止是加法。Type C（推翻架构、A 方案被 B 取代）时，旧内容必须**删除或替换**，不能无脑保留。"增量更新"≠"只增不删"。

2. **标记每处变更及其驱动 CR**：在被改动的章节就近标注（如 `<!-- 变更 v{n}：新增 B 表，驱动 {ticket}-CRv{n} -->` 或在小节标题旁注明），使门控人能定位本次 delta，只 review 变更面。

3. **一致性扫描（强制）**：应用 delta 后，全文扫一遍被本次变更波及的**衍生表述**——汇总句、计数（如"本设计含 N 张表"）、交叉引用、概要章节、目录——逐处同步更新。只改局部不扫全局会留下"概要说 1 张表 / 正文已 2 张表"这类矛盾。一致性扫描是增量更新模型的安全网，不可跳过。

> 三条约束共同保证：正文始终是**单一当前真相、无并存旧版片段**（满足"防 AI 锚定过期内容"的原目标），但到达方式是无损的"就地编辑"而非有损的"重生成"。

### 历史留存（两种类型通用）

1. **变更履历 = 文档表头轻量表**：
   ```markdown
   | 版本 | 日期 | 变更摘要（改了什么 + 为什么） | 驱动 CR | 执行者 |
   |------|------|------------------------------|---------|-------|
   ```

2. **旧全文 = git + `_history/` 快照**：
   - 所有文档通过 git history 追溯（可 diff vN ↔ vN+1 看完整变更）
   - **核心产物**（requirements.md、design.md、solution-design.md）在 Type B/C 重跑前，额外快照到 `_history/{filename}.v{n}.md`

| 文档类别 | 重跑写入 | 表头变更履历 | `_history/` 快照 |
|---------|---------|:-----------:|:----------------:|
| 核心产物（requirements.md / design 主文档 / solution-design） | 增量更新 | 必须 | Type B/C 必须 |
| 一般产物（api_design / schema / 测试用例 / 造数脚本等） | 增量更新 | 必须 | 否 |
| delta 文档（00_impact_analysis.md） | 覆盖 | 必须 | 否 |

---

## 关键原则

1. **路由，不执行**：只分析影响范围、更新状态、产出清单
2. **精准标注**：只将真正受影响的产物标为 ⚠️
3. **门控优先**：分类必须经人类确认，不自动执行
4. **跨 Workbench 安全不妥协**：跨 Workbench 涟漪绝不被单个 Workbench 工程师静默路由
