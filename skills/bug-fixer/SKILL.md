# Bug Fixer

基于 Bug 报告，通过静态代码分析定位根因，实施最窄范围修复。

> **本 Skill 的分层**：下文为**各 Workbench 通用**的修复纪律（静态分析、最窄修复、回归强制）。
> 本 Workbench"用什么命令定位代码、用什么命令跑回归"这类技术绑定内容，运行时从 `references/{role}.md` 加载。

---

## Memory 契约

### 始终加载（每次执行前必读）
- `local_profile.yaml` — 获取当前工程师的 role 和 code_roots（必须存在）
- `project-memory/project_glossary.md` — 项目术语表
- `project-memory/architectural_constraints.md` — 架构约束

### 始终加载（续）
- `references/{role}.md` — **本 Workbench 定位/验证参考**（role 来自 local_profile.yaml）

### 按需加载
- `{Workbench_root}/01_requirements/requirements.md` — 仅在出现"正确行为存疑"时加载
- `{Workbench_root}/04_design/design.md` — 仅在定位到具体模块后，确认修复方向时加载（不全量加载）
- `{{REQUIREMENTS_DIR}}/{ticket-id}/_progress.md` — 仅在用户提供了票据 ID 时加载

| 输入 | 必填 | 说明 |
|------|------|------|

## 输出

- 修复后的代码变更（直接编辑相关文件）
- 修复摘要（根因 + 变更内容 + 回归测试结果）

---

## Guardrails

| 规则 | 触发条件 | 执行动作 |
|------|---------|---------|
| **local_profile 缺失** | `local_profile.yaml` 不存在 | BLOCK：必须先创建并声明 role |
| **禁止主动读取环境日志** | 尝试访问日志文件或运行环境 | BLOCK：只接受用户主动提供的日志文本 |
| **禁止推断根因** | 无代码证据支撑的根因判断 | 标注 ⚠️ 待确认，不直接断言 |
| **禁止 Fix 范围外的改动** | 修复代码中包含与 Bug 无关的重构或优化 | BLOCK：移除无关改动，仅保留最窄修复 |
| **大文件禁止全量加载** | 代码文件超过 300 行 | 使用 grep/head/blame 定位关键行，不全量加载 |
| **修复超出 3 个文件** | 变更涉及超过 3 个文件 | WARN：列出变更文件清单，要求人类确认 Scope 合理后再继续 |
| **无法定位根因** | 穷尽可用线索后仍无法定位 | BLOCK：列出已分析范围和需要用户补充的具体信息 |

## 执行流程

### 前置条件检查

-1. 读取 `local_profile.yaml`（获取 role、code_roots；code_roots.{role} 必须存在）；**加载 `references/{role}.md`**
0. 读取本 Workbench 仓库的 `AGENTS.md`（从 `code_roots.{role}` 拼接路径）。**优先级 1=AGENTS.md；缺失则回退读同路径 `CLAUDE.md`（优先级 2）；两者皆无 → BLOCK，提示用户先在该仓库补充 agent 文档后重跑，不得凭空定位代码**
0.5 若用户提供了票据 ID：读取 `{{REQUIREMENTS_DIR}}/{ticket-id}/_progress.md`（了解该功能的实现阶段、历史变更文件）

---

### Phase 0：Human Pre-Screen

**在读任何代码前**，向用户提问：

> "在我开始分析代码之前，你对这个 Bug 有什么初步判断？
> 例如：怀疑哪个模块、哪个接口、哪段逻辑？"

- **用户提供线索** → 以此为起点缩小搜索范围
- **用户选择跳过** → 基于 Bug 描述全量分析

---

### Phase 1：Locate（静态代码定位）

**原则**：纯静态分析，不依赖运行环境。

**定位策略**（按优先级）：

1. **从用户线索出发**：直接定位到怀疑模块，用 head/grep 读取关键方法
2. **从 Bug 描述的关键词出发**：按 `references/{role}.md` 的「代码定位命令」执行本 Workbench 的 grep/find 搜索
3. **从日志/堆栈的类名和行号出发**（若用户提供）：直接定位到对应文件和行号

**决策原则**：
- 找到相关代码 → 用 head/grep/blame 读取关键逻辑，**不全量加载**大文件
- 定位到具体模块后 → 若存在 `{Workbench_root}/04_design/design.md`，加载该模块对应设计节，确认修复方向**不违反设计意图**（分层约定、幂等策略、缓存失效规则等）
- 发现"正确行为存疑" → 按需加载 `requirements.md` 确认原始意图
- 无法从代码直接确认的归因 → 标注 `⚠️ 待确认`，不猜测

**Phase 1 产出**（在对话中呈现，不写文件）：

```
根因定位报告：
- 文件：{file_path}:{line_number}
- 问题代码：{引用代码片段}
- 根因分析：{说明为什么这段代码导致了该 Bug}
- 最小变更范围：{预计需要改动的文件列表}
⚠️ 待确认：{无法直接从代码确认的疑点（若有）}
```

**呈现后等待用户确认根因定位，再进入 Phase 2。**

---

### Phase 2：Fix（最窄修复）

**原则**：只改修复 Bug 所必须的代码，不做重构、不做优化、不调整无关逻辑。

1. 基于 Phase 1 的根因定位实施代码修改
2. 自检：每处改动是否与根因直接相关？若有无关改动立即还原
3. 修改完成后呈现 diff 供用户 review

---

### Phase 3：Verify（回归验证）

按 `references/{role}.md` 的「回归验证命令」运行本 Workbench 测试（命令直接写在 reference 内，Phase 2 采集所得）。

1. 运行触碰模块的相关测试
2. 若 Phase 1 有"正确行为存疑"标注 → 加载 `requirements.md`，确认修复后行为符合原始 AC
3. 测试通过 → 输出修复摘要
4. 测试失败 → 分析失败原因，修正后重新验证（最多 2 次）；仍失败 → BLOCK，上报人类

---

## 人类门控

| 门控点 | 参与者 | 通过标准 |
|--------|-------|---------|
| 根因定位确认（Phase 1 后） | 工程师 | 定位符合预期，或补充修正方向 |
| 变更 Scope 确认（超 3 个文件时） | 工程师 | 确认变更范围合理 |

---

## 验证回路

- **根因有代码证据**：每条根因判断必须引用具体 `文件:行号`
- **修复最窄**：diff 中不含与 Bug 无关的改动
- **回归通过**：触碰模块的已有测试全部通过
- **推断标注**：无代码证据支撑的内容必须标注 ⚠️

---

## 关键原则

1. **分析优先于修复**：没有根因定位就不动代码
2. **人工线索先于全量搜索**：Phase 0 的 2 句话可能节省大量搜索 context
3. **最窄修复**：只改必须改的，其他问题开新 ticket
4. **静态分析边界**：不访问运行环境，日志只接受用户提供
5. **回归强制**：每次修复必须运行相关测试，不允许跳过
